### 1.2 玩法循环

一局的阶段由 `GamePhase` 状态机驱动（`formal/include/tribe/game_state.hpp:17`）：
`Managing`（经营）→ `Mission`（可操控小队地图任务）→ `War`（可操控战争）→ `EndingChoice`（时代结算选择）→ `Finished`（结局）→ `Sandbox`（长期模式结局后沙盒，`game_engine_season.cpp:269-277`）。

循环的六个环节与代码归属：

1. **经营**：`assign` 分配劳力 / `build` 建造 6 种建筑 / `research` 研究 9 项技术 / `craft|repair|scrap|equip|unequip|appoint|unappoint|treat|squadrest`。
   实现集中在 `formal/src/game_engine_management.cpp`（363 行），成本表见 `game_engine_management.cpp:35-36`（建筑木材/石料）与 `:61-62`（技术食物/木材按 `tier` 递增）。
   本季行动点由 `availableTeams()` 决定：`min(7, 3 + 已配置资源队数)`（`game_engine.cpp:166-171`）。
2. **地图任务**：`mission`/数字 `5`/`mission outpost` 派队出发（`game_engine_mission.cpp:31-124`），进入 `Mission` 阶段后在 16 地点地图上 `move`/`gather`/`build outpost`/`settle`/遭遇战/地图内 `use herb`，由 `ExpansionGame` 独占处理（`game_engine_mission.cpp:126-285`）。
3. **外交**：`talk|gift|trade|openroute|marry|tribute|demand|ally|declare|truce|raid|appease`（`formal/src/game_engine_diplomacy.cpp`，342 行）。每季每个部落只允许一次"主动外交"，靠编年史标记实现（`game_engine_diplomacy.cpp:31-41`）。
4. **战争**：`declare` → `formarmy` → `war <部落>` 进入 `War` 阶段 → `order|attack|defend|retreat`（`formal/src/game_engine_war.cpp`，257 行）。
5. **季结算**：`endturn` → `endSeason()`（`game_engine_season.cpp:172-235`）依次做：食物消耗与朝贡 → 其它部落自主变化 → 玩家派系危机 → 据点驻军动乱 → 前哨荒废 → 生成新的待决事件 → 覆灭判定 → 是否进入 `EndingChoice` → 否则 `++season` 并重置行动点。
6. **结局**：`choose <alliance|conquest|prosperity|migration>`（`game_engine_season.cpp:256-267`）由 `availableEndings()` 判定条件（`game_engine_season.cpp:237-254`）：联盟（2 个盟友 + 河鹿/白羽关系 ≥70 + 部落联盟技术）、征服（2 个外部据点 + 战士 ≥5 + 士气 ≥55）、繁荣（人口 ≥20 + 食物 ≥40 + 建筑 ≥4 + 技术 ≥4）、迁徙（无条件）；人口或营地耐久归零走覆灭（`game_engine_season.cpp:161-170`）。

### 3.3 "候选状态 + validateState + commit" 原子提交模式

**先纠正一个常见误解**：`commit` / `rejected` **不在** `game_engine_internal.hpp` 里。它们是 `GameEngine` 的私有成员函数，声明在 `formal/include/tribe/game_engine.hpp:220-226`，定义在 `formal/src/game_engine.cpp:144-158`。`game_engine_internal.hpp` 提供的是所有分片共用的辅助函数集合（`game_engine_detail` 命名空间）：`enumInRange`（`:16-20`）、`validStoredItem`（`:26`）、`sameItem`（`:28`）、`parseNonnegative`（`:30`）、各类中英别名解析（`:32-56`）、`relationClamp`/`percentClamp`（`:72-74`）、`countTrue`（`:90-93`）、疲劳与工艺/医疗等级（`:70, 106-116`）等；它们的共同契约是"不修改游戏状态，失败返回空/false 或写出错误"。

提交路径（`GameEngine::commit`，`game_engine.cpp:144-154`）分三步，注释里也写明了：

```cpp
ActionResult GameEngine::commit(GameState candidate, std::string message, const bool consumesAction,
                                const bool seasonAdvanced, const bool endingReached) {
    population_rules::refreshWorkforceReassignment(candidate);   // 1. 先重算派生字段
    std::string error;
    if (!validateState(candidate, error)) return rejected("行动后的状态未通过校验，已原子取消：" + error);  // 2. 全量校验
    state_ = std::move(candidate);                                // 3. 校验通过才唯一一次替换
    return {true, true, true, consumesAction, seasonAdvanced, endingReached, std::move(message)};
}
```

配合的辅助函数：
- `rejected()`（`game_engine.cpp:156-158`）返回 `{recognized=true, success=false, stateChanged=false, ...}`，即"命令被识别但被拒绝"。
- `canSpendAction()`（`game_engine.cpp:132-142`）在阶段与行动点不足时用 `rejected` 填满调用方的结果对象并返回 false，是各规则函数的统一前置门禁。
- `spendAction(candidate)`（`game_engine_diplomacy.cpp:43`）只减候选状态；`addChronicle(candidate, ...)`（`game_engine.cpp:160-164`）只追加候选状态并裁剪到 200 条；`finalizeDiplomacy(candidate, tribe)`（`game_engine_diplomacy.cpp:38-41`）同样只写候选状态——三者都带"必须在 commit 前对 candidate 调用"的注释约束。

地图层有**同构的第二套**实现：`ExpansionGame::commit`（`expansion_game.cpp:536-542`）与 `ExpansionGame::rejected`（`:544-546`），所有地图操作都写成 `ExpansionState candidate = state_;` → 改 `candidate` → `recordTurn(candidate, ...)` → `commit(...)`。

### 3.4 "失败路径不改状态"这条不变量怎么被保证

四道互相独立的保证：

1. **结构上只有一个写入点**。全仓库对 `GameEngine::state_` 的赋值只有两处：`game_engine.cpp:152`（commit）与 `game_engine_validation.cpp:49`（`replaceState`，先 `validateState` 再赋值）。`ExpansionGame` 对 `state_` 的赋值只有 `expansion_game.cpp:540`（其构造期初始化在 `:125-139`，构造函数在 `:142-145` 校验）。任何规则函数都只能改形参 `GameState& candidate`，无法绕过。
2. **规则函数签名不接收 state_**。例如 `build/research/...` 全部返回 `ActionResult` 且不接触 `state_`；`settleFactions`/`settleAutonomousTribes` 这类季结算规则接收 `GameState& candidate`（`game_engine_season.cpp:31, 55, 120`）。
3. **校验是提交的前置条件**，并且读取路径复用同一校验：`save_codec::readGameState` 末尾调用 `GameEngine::validateState(state, error)`（`save_codec.cpp:899`），`SaveRepository::save` 先 `validateState` 再序列化（`save_repository.cpp:101-104`），`GameEngine(GameState)` 构造也校验（`game_engine.cpp:127-130`）。因此"能从存档读出来"与"能被提交"是同一套判决。
4. **测试用官方编解码给状态做字节快照**来证明失败命令是"零改动"：`current_game_tests.cpp:31-54` 的 `stateSnapshot` + `requireRejectedWithoutChange`，并用固定种子跑 160 步随机命令，每一步都与循环前的字节快照比较（`:539-553`）。这条测试对成员3的任何改动都极其敏感——**只要失败路径意外改了状态，`save` 出来的字节就会变，测试立刻失败**。

## 4. 命令系统

### 4.1 规范化（`formal/src/command_parser.cpp`）

- `parse(input)`（`command_parser.cpp:23-30`）：用 `std::istringstream >>` 按任意空白切分，第一个词是 `verb`，其余是 `args`；**对每个词元只把 ASCII 字母转小写**（`asciiLower`，`:13-19` 逐字节判断 `byte < 128U`），中文字节原样保留。这保证了 `move forest`、`移动 苍林`、`  move   forest  ` 三种写法等价（测试 `map_mission_tests.cpp:163-176` 与 `current_game_tests.cpp:119-147` 都验证了这一点）。

### 4.3 `hasArity` 参数校验

`hasArity(command, expected)`（`game_command_catalog.cpp:78-80`）是**精确相等**判断（`args.size() == expected`），不区分"参数太少"和"参数太多"。调用方统一写成三目表达式，例如：

- `game_engine_dispatch.cpp:91`：`hasArity(command, 0U) ? viewed(statusText()) : rejected("用法：status / 状态")`。
- `game_engine_dispatch.cpp:210-211`：`equip` 必须刚好 3 个参数。
- 少数命令用**范围**判断而不是 `hasArity`：`squad configure` 要求 `args.size() >= 3U`（`:101`）、`formarmy` 允许 2 或 3 个参数（`:340`）、`mission` 允许 `<= 1` 个参数（`:155`）。

### 4.4 dispatch 的分发顺序（含 abort 特判）

入口 `GameEngine::execute`（`game_engine_dispatch.cpp:26-34`）顺序固定为：

1. `command_parser::parse(input)`；空动词直接返回默认回执（`:27-28`）。
2. `game_command_catalog::classify(command)`（`:30`）。
3. **按阶段路由**（`:31-33`）：`Mission → dispatchMissionCommand`；`War → dispatchWarCommand`；其余（`Managing`/`EndingChoice`/`Finished`/`Sandbox`）→ `dispatchManagingCommand`。

`dispatchMissionCommand`（`:38-50`）的第一件事就是 **abort 特判**：

```cpp
if (commandId == CommandId::Abort && hasArity(command, 0U)) {
    GameState candidate = state_;
    if (!candidate.squads.empty()) candidate.squads.front().station = WorldLocationId::Camp;
    candidate.activeMission.reset();
    candidate.phase = GamePhase::Managing;
    candidate.stability = std::max(0, candidate.stability - 2);
    addChronicle(candidate, 1, "任务中止", "小队提前返回，部落稳定略有下降。");
    return commit(std::move(candidate), "小队放弃当前载货并返回营地。", false);
}
return executeMission(input);
```

即：`abort` 由**上层 GameEngine 自己处理**（因为要改 `phase`、`station`、`stability` 这些部落级字段），其余所有命令转发给 `executeMission(input)`，最终落到 `ExpansionGame::execute`（`game_engine_mission.cpp:162-165`）。这一特判必须排在转发之前，否则地图层的 `ExpansionGame` 不认识 `abort`（其 `execute` 只识别 look/map/move/gather/attack/defend/retreat/use/build(outpost)/settle，`expansion_game.cpp:147-183`）。

`dispatchWarCommand`（`:54-70`）：只接受 `order <军令>`（校验 `parseWarOrder`）、`attack`、`defend`、`retreat`，以及 `status`/`look`（0 参数）返回一行战争摘要；其它一律 `rejected("战争中可用：攻击、防御、下令、撤退、状态。")`。

`dispatchManagingCommand`（`:86-357`）的内部门禁顺序（顺序本身就是规则，改动会改变玩家可见行为）：

1. 先处理 8 个只读视图：`Status`→`statusText`、`Map`→`worldText`、`Diplomacy`、`Factions`、`Squads`、`Objectives`、`Chronicle`、`Help`（`:90-113`）；`Squad` 只有在 `squad configure ...` 形态下才继续（`:100-103`）。
2. `Finished` 阶段：只允许 `sandbox`，否则拒绝（`:118-121`）。
3. `EndingChoice` 阶段：只允许 `choose <1 参数>`，否则拒绝（`:122-128`）。
4. 非结算阶段输入 `choose` → 提前给出"现在还不能选择结局…输入 endturn"的**识别但拒绝**回执（`:129-132`，测试 `current_game_tests.cpp:555-568` 专门锁定这条）。
5. 人口门禁：`workforceReassignmentRequired` 为真时只放行 `allowsWorkforceRecovery` 白名单（`assign` 合法岗位 / `assign outpost` / `garrison` / `disbandarmy` / `event`，见 `:74-82`），否则拒绝（`:133-135`）。
6. 待决事件门禁：`pendingEvent.active` 且不处于人口门禁时，除 `event` 外全部拒绝（`:136-138`）。
7. 最后才是按 `CommandId` 的大 `switch`（`:140-356`），每个分支内部再做 `hasArity` 与别名解析；未命中的分支 `break` 后统一 `return {}`（`:357`），即"未识别"。

### 4.5 地图命令复用同一命令目录

`ExpansionGame::execute`（`expansion_game.cpp:147-183`）同样调用 `game_command_catalog::classify` 和 `hasArity`，因此**地图命令词表与主引擎共享同一张表**。这意味着"给地图加一条新命令"必然要改 `formal/src/game_command_catalog.cpp`（枚举 + classify），而该文件同时被主引擎所有阶段使用——这是成员3范围内**最容易与他人的改动冲突**的文件，详见 §7.4。

地图层的额外规则：遭遇战期间（`encounterLife > 0`）道路封锁，除 `look`/`map`/`attack`/`defend`/`retreat` 外全部拒绝（`expansion_game.cpp:155-161`）。

### 5.3 文件格式与 `kSaveVersion = 6`

- 版本常量：`constexpr int kSaveVersion = 6;`（`game_state.hpp:83`，注释说明 v6 用"持久化的全局序号"保证制造物品跨仓库转移后编号唯一）。
- 文件布局（`save_codec.cpp:906-928` 写入 / `:932-972` 读取）：
  `magic "TRIBESAV"(8B)` → `u32 version` → `u32 payloadSize` → `u32 FNV-1a checksum(payload)` → `payload`。
  - magic 定义 `save_codec.cpp:18`；checksum 算法 `:167-174`（FNV-1a 32 位，初值 `2166136261`、质数 `16777619`）。
  - 版本白名单：**只接受 6 和 5**（`:944`），其它版本报 "旧版本存档不支持，需要新开局；原文件未被修改。"
  - 长度上限：`kMaximumSaveBytes = 16 MiB`（`:19`），`payloadSize > kMaximumSaveBytes` 直接拒绝（`:948`）。
  - 读取端要求**载荷被完整消费**：`!payloadReader.finished()` → "存档包含未识别的尾部字段。"（`:964-967`）。
  - 读取端还要求 `fileReader.finished()`（`:953`），即文件不得有尾随字节。
- 所有多字节整数为小端；`writeInt/readInt` 用 `memcpy` 保存位模式并 `static_assert(sizeof(int) == 4)`（`:44-50, 117-125`）；布尔只接受 0/1（`readBool`，`:129-134`）；字符串是 `u32 长度 + 原始 UTF-8 字节`（`:62-70, 147-154`），单条上限 `kMaximumStringBytes = 1 MiB`（`:20`）。

### 5.4 `writeExpansionState` / `readExpansionState` 的定长顺序编解码

写入：`save_codec.cpp:379-403`。读取：`save_codec.cpp:407-424`。两者字段**一一对应且顺序完全一致**：

```cpp
// 写入（save_codec.cpp:379-403）
writeU32(seed); writeInt(turn); writeEnum(phase);
writeExpansionSquad(squad); writeInventory(backpack);
writeBool(settled); writeInt(worldLocation);
writeBoolArray(worldDiscovered); writeBoolArray(outposts);      // 各 16 字节
writeInt(cargoFood); ...; writeInt(cargoHides);                  // 5 个载货字段
writeInt(harvestActions); writeInt(cargoCapacity);
writeInt(foodGatherBonus); writeInt(herbGatherBonus);
writeEnum(missionKind); writeEnum(assignedResource);
writeInt(crewSize); writeInt(encounterLife); writeBool(encounterDefeated);

// 读取（save_codec.cpp:407-424）：同样的调用顺序，每个枚举都做闭区间校验
readEnum(phase, Exploring, Settled);
readExpansionSquad → readInventory → readBool(settled) → readInt(worldLocation) →
readBoolArray(×2) → readInt(×7) → readEnum(missionKind, Gather, OutpostConstruction) →
readEnum(assignedResource, Food, Hides) → readInt(×2) → readBool → 
最后 return static_cast<bool>(ExpansionGame::validateState(state));   // :423
```

注意读取端在返回前**必须通过 `ExpansionGame::validateState`**（`save_codec.cpp:423`），所以"能读出来"等价于"地图层认为合法"；`squad` 里的每个 `Character` 由 `readCharacter`（`:284-314`）逐字段校验（属性 1..20、等级 >0、装备槽必须与 `equipmentSlot` 匹配），`backpack` 由 `readInventory`（`:327-342`）用 `Inventory::pickupFree` 重放装载过程（容量不足即判定损坏）。

### 5.5 ⚠️ ExpansionState 的字段顺序与数量被存档格式锁定

**这是成员3最需要记住的一条硬约束：**

> **`ExpansionState` 的字段顺序与数量被 v6 存档格式锁定。新增、删除、重排任何字段都会破坏 v6 兼容。**

理由与证据：
1. `readExpansionState` 是按固定顺序的**无字段名**二进制读取（`save_codec.cpp:407-424`），没有 TLV、没有字段计数、没有版本子号；多读/少读一个字段会导致后续所有字段**错位**。
2. `deserializeFile` 在解析后强制要求 `payloadReader.finished()`（`save_codec.cpp:964-967`）。如果只在**末尾**追加字段，旧 v6 存档会因"少一段字节"在 `readExpansionState` 中途读失败（报 "存档的活动任务损坏。"，`:804-807`）；如果只在 `writeGameState` 里追加而读取端不追加，则会命中 "存档包含未识别的尾部字段。"
3. 版本号是**整份文件一个**（`kSaveVersion`，`game_state.hpp:83`，`save_codec.cpp:917`），没有"载荷内部版本"。因此任何布局变动都必须**同时**修改 `writeGameState/writeExpansionState` 与 `readGameState/readExpansionState`，并升 `kSaveVersion`；否则老档要么读不出，要么被静默错读（错位后大概率被 `validateState` 拦住，报"存档的活动任务损坏"，但这是**拒绝**而不是迁移）。
4. v5→v6 迁移链进一步依赖"v5 载荷 = v6 载荷去掉尾部 4 字节 `nextItemSerial`"这一事实：`asV5` 夹具就是 `substr(0, size-4)` 并重算校验和（`save_repository_tests.cpp:86-99`），迁移时还会做内存复解析并比对序号（`save_file_transaction.cpp:293-299`）。改动布局会同时打断 v5 迁移与这两个测试。

**实践建议**：确实要给地图加持久化字段时，正确做法是升 `kSaveVersion` → 加 `readExpansionState` 的兼容分支（按 `version` 决定读写哪些字段，参照现有 `containsItemSerial` 参数的写法，`save_codec.cpp:725, 891-898`）→ 更新 `save_repository_tests.cpp` 的 v5/v6 夹具；只改一处必然编译通过但读取失败。**纯展示用的新数据（如 `world_map_catalog.cpp:166-185` 的 `kProfiles`）放目录表里、不进 `ExpansionState`，是零兼容风险的扩展方式**（`world_map_catalog.hpp:23`、`expansion_game.hpp:92` 都明确写了"不影响 v6 存档兼容"）。

### 5.6 v5→v6 迁移

- 触发点：`SaveRepository::load` 读到 `primaryVersion == 5` 时调用 `migrateV5`（`save_repository.cpp:131-140`）；`.bak` 与 `.tmp` 来源也各自支持（`:156-159, 172-176`）。
- `migrateV5File`（`save_file_transaction.cpp:290-347`）步骤：内存 `serialize` v6 → 内存 `deserialize` 复解析并比对 `nextItemSerial`（`:293-299`）→ 原子归档原始字节为 `.v5.bak`（`:301-303`，`copyFileAtomically` 拒绝覆盖已存在的归档，`:204-218`）→ 写 `.v6-migrate.tmp` → 磁盘复解析且校验版本号（`:330-339`）→ `replaceMigratedPrimary` 原子替换（`:243-284`，失败时把旧主档改回原名）→ 成功后用磁盘复解析结果覆盖 `parsed`（`:345`）。
- `nextItemSerial` 的 v5 推导：`deriveNextItemSerial`（`save_codec.cpp:697-720`）扫描 `stockpile`、`war.lockedEquipment`、`roster` 装备、活动任务的背包与成员装备，取出制造编号最大值 +1；序号耗尽（等于 `u32` 最大值）则拒绝迁移（`:714-717`）。制造编号的识别规则见 `manufacturedItemSerial`（`:678-693`），只认 9 种配方前缀（`knife/spear/shield/armor/shoes/flintspear/reinforcedshield/cloak/charm`）。
- 迁移信息通过 `SaveLoadInfo{migratedFromV5, legacyBackupPath}` 回传给界面（`save_repository.hpp:42-45`），`application.cpp:201-202` 会提示"已从 v5 升级；原始档保留在 xxx.v5.bak"。

### 5.7 原子写文件（`save_file_transaction`）

`writeAndVerify`（`save_file_transaction.cpp:13-105`）的顺序是**"临时写入 → 验证 → 轮换备份 → 替换主档"**：

1. 校验器为空直接拒绝（`:15-18`）；`create_directories` 建目录（`:20-24`）。
2. 删除旧 `.tmp`（`:30-34`），写 `.tmp` 并 `flush`/`close` 且每步检查流状态（`:36-53`）。
3. 调用 `verifyV6Temporary`（`:56-60`）——它走的是**与正式读取完全相同的链路** `loadFile → save_codec::deserialize`（`:116-154, 158-161, 368-370`）。
4. 主档存在则：删旧 `.bak` → `rename(主档 → .bak)`（`:68-81`）。
5. `rename(.tmp → 主档)`；若失败且曾有主档，则尝试把 `.bak` 改回原名，并把真实错误与恢复结果一起报给玩家（`:84-100`）。

读取与恢复策略（`SaveRepository::load`，`save_repository.cpp:119-189`）：
- **主档 I/O 不可用（`Unavailable`，如权限/非普通文件）时保守失败**，明确"为避免误读旧备份，本次没有自动回退"（`:141-145`）——注意这**不会**去尝试 `.bak`。
- 主档缺失或损坏（`Missing`/`Invalid`）才依次尝试 `.bak`、`.tmp`，成功则 `restoreRecovered` 回写主档（`:147-184`）。

### 5.9 `nextItemSerial` 的唯一编号策略

- 语义：`GameState::nextItemSerial`（`game_state.hpp:242`，注释"必须为正数，且只会递增而不会复用"）。
- 制造时（`game_engine_management.cpp:199-206`）：先判 `nextItemSerial == 0 || == u32 最大值` 拒绝（"装备编号已耗尽"），再用
  `item.id = key + "_" + season + "_" + std::to_string(nextItemSerial++)`，即形如 `spear_3_7`。
  注释明确写了动机：物品可能已被装备/携带/报废，**不能以仓库大小作为编号来源**。
- 提交后校验（`game_engine_validation.cpp:330-333`）：用 `manufacturedSerial`（`:30-41`）从所有位置的物品 id 中反查最大序号，要求 `nextItemSerial > 最大序号`，否则拒绝提交。这条把"序号只增不复用"从约定升级成了**提交时强制的不变量**。
- 存档读取时 `nextItemSerial == 0` 直接判损坏（`save_codec.cpp:891-895`）。
- 对照：地图的岩牙徽记 id 不走这套序号，而是 `"rockfang_badge_" + seed`（`expansion_game.cpp:318`）。两者都靠 `GameEngine::validateState` 的所有权集合（`itemOwners`，`game_engine_validation.cpp:153, 181, 265, 272, 313`）兜底唯一性——一旦出现重复 id，**整个任务结算会被原子拒绝**（见 §8 风险 3）。

## 6. 测试体系

### 6.1 自研测试框架

`tests/test_harness.hpp`（42 行）：
- `test::registry()`（`:14-17`）是一个函数内静态 `vector<pair<string, TestFunction>>`，`Registrar`（`:19-24`）在构造时把用例登记进去——**测试用例通过全局静态对象自动注册**。

### 7.3 地图子系统的数据流（成员3视角的一张图）

```
startMission ──► ExpansionState{ squad 从 roster 复制, backpack 重建, worldLocation=station,
                                 worldDiscovered/outposts 从部落复制, cargoCapacity=f(crewSize) }
                        │
                        ▼  （保存进 GameState.activeMission，GameState.phase=Mission）
        GameEngine::execute ──► dispatchMissionCommand
                        │            ├─ abort ──► 丢弃 activeMission（载货/背包/经验全丢，稳定-2）
                        │            └─ 其它 ──► executeMission
                        │                          ├─ 外交动词 ──► proxy GameEngine（位置决定对象，discovered 提前回写）
                        │                          └─ 地图动词 ──► ExpansionGame::execute
                        │                                             └─ 每个操作：candidate = state_
                        │                                                → 改 candidate → recordTurn → commit(validateState)
                        ▼
             mission.state().phase == Settled ?
                        ├─ 否：candidate.activeMission = mission.state()，一次 commit（不消耗行动点、不入账）
                        └─ 是：++missionCount → 载货五行入部落库存 → 背包并入 stockpile → 角色/小队/驻地同步
                               → 疲劳与最高等级重算 → 覆灭判定 → 一次 commit（地图层永不直接写部落库存）
```

**关键不变量（改代码时必须维持）**：
1. 地图层只产生载货，**部落库存的唯一入账点是 `game_engine_mission.cpp:179-183`**；`ExpansionGame` 自身不碰 `GameState`。
2. 只有 `settle()`（`expansion_game.cpp:285-301`）能把任务置为 `Settled`；`executeMission` 是唯一消费 `Settled` 的地方（`game_engine_mission.cpp:170`）。任何新增的"提前结束任务"入口都必须自己负责入账或明确丢弃。
3. 任务内角色是 `roster` 角色的**镜像**，装备在任务期间不流转；这条由 `validateState`（接触面 #6）强制，改动镜像语义会立刻让校验失败。
4. `discovered/outposts` 在任务期间只能"任务 ⊇ 部落"，结算时才整体回写。

### 风险 1［高］`ExpansionState` 字段顺序与数量被存档格式锁定

- 证据：`save_codec.cpp:407-424`（无字段名的定长顺序读取）＋ `save_codec.cpp:964-967`（要求载荷被完全消费）＋ `save_codec.cpp:944`（版本白名单只有 5 和 6）＋ `save_file_transaction.cpp:293-299`（v5 迁移前的内存复解析与序号比对）＋ `save_repository_tests.cpp:86-99`（v5 夹具＝v6 载荷截去尾部 4 字节）。
- 后果：给 `ExpansionState` 加字段若不同时升版本并写兼容分支，旧 v6 档会读失败（"存档的活动任务损坏。" / "存档包含未识别的尾部字段。"）；更糟的是**静默错读**的可能——错位后的字节仍可能凑出"看起来合法"的数值，只有 `validateState`（`save_codec.cpp:423`）能兜住大部分情况，但不能保证全部。
- 建议：任何字段变更走"升 `kSaveVersion` + 双版本读取 + 更新 v5/v6 夹具 + 补一条迁移测试"的完整流程；纯展示数据放目录表（如 `kProfiles`），永不进 `ExpansionState`。

### 风险 2［中］"已结算却仍挂载"的 Mission 状态

- 证据：`game_engine_validation.cpp:278-329` 在 `phase == GamePhase::Mission` 时只要求"存在 activeMission 且它自身合法"，而 `ExpansionGame::validateState` 允许 `phase == Settled`（`expansion_game.cpp:475-476`），**没有任何一条断言要求 `activeMission->phase == Exploring`**。因此 `phase=GamePhase::Mission` + `activeMission.phase=Settled` 是一个可以通过 `validateState`、可以存档、可以 `replaceState` 的合法状态。
- 影响：目前**不会**导致重复入账，因为 `executeMission` 只在 `mission.state().phase == Settled` 时走结算分支（`game_engine_mission.cpp:170`），而二次 `settle` 会被地图层拒绝（`expansion_game.cpp:286`）。但该状态下每一条地图命令的安全性**完全依赖各自函数手写的 phase 门禁**：`expansion_game.cpp:186`（move）、`:204`（gather）、`:269`（buildOutpost）、`:286`（settle）、`:305`（attack）、`:337`（defend）、`:349`（retreat）、`:365`（useHerb）。快照里的 8 条都齐全——但**这不是一开始就是这样**：本次并发编辑（09:45）之前，`useHerb`/`attackEncounter`/`defendEncounter`/`retreatEncounter` 都**没有** phase 门禁，属于会改到已结算任务回合的真实缺陷，现在已被修复（`expansion_game.cpp:304-305, 337, 349, 364-365`）。
- 建议：把 phase 门禁提到 `ExpansionGame::execute` 的统一入口（像 `encounterLife > 0` 那样在 `:155-161` 集中拦截），或直接在 `GameEngine::validateState` 加一条"任务阶段必须 `Exploring`"的断言，让"新增地图命令忘记加门禁"这一类问题在结构上不可能发生。

### 风险 3［中］`missionCount` 在 `abort` 与 `settle` 之间的不对称

- 证据：结算路径 `++candidate.missionCount`（`game_engine_mission.cpp:174`）；`abort` 路径（`game_engine_dispatch.cpp:40-48`）**完全不动 `missionCount`**，也不写 `missionDeaths`、不减疲劳、不退还行动点。而任务种子依赖它：`missionSeed = seed + season*97 + missionCount*17`（`game_engine_mission.cpp:71-72`）。
- 影响一（可复现性）：同一季 `abort` 后再出发会得到**完全相同的 `missionSeed`**，即相同的遭遇与事件走向——如果玩家把 abort 当成"重抽任务"，这在设计上也许是可接受的，但它没有文档化，也没有测试固定这一行为。
- 影响二（编号安全）：岩牙徽记的 id 只由 seed 派生（`expansion_game.cpp:318`，`"rockfang_badge_" + seed`），不走 `nextItemSerial`。目前不会撞车，因为 `missionCount` 在每次成功结算后 +1，而 abort 会丢弃背包与载货；但一旦有人为了"让 abort 也计数"而改动 `missionCount` 语义，或把徽记 id 逻辑挪到别处，就可能出现两枚同 id 徽记，届时 `GameEngine::validateState` 的 `itemOwners` 唯一性检查（`game_engine_validation.cpp:153, 265`）会让**整个任务结算被原子拒绝**——表现为"任务背包物品编号冲突，回营结算已原子取消"，玩家一次任务的收获全部丢失。
- 影响三（提示文案）：`firstSeasonGoal`（`console_ui.cpp:110-115`）与 `roadProgress`（`:119-136`）都用 `missionCount > 0` 判断是否展示；abort 不计数意味着首季目标会一直显示，行为上是合理的，但依赖了一个隐式约定。
- 建议：明确 `missionCount` 的语义（"成功结算次数"还是"派队次数"）并写进注释；给徽记改用 `nextItemSerial` 风格的唯一编号，或在 `ExpansionGame::validateState` 内显式校验徽记 id 与 seed/missionCount 的关系。

### 风险 4［中］`validateState` 的顺序短路与死分支

- 证据（死分支）：`game_engine_validation.cpp:88` 已经要求 `candidate.workforceReassignmentRequired == (overage > 0)`，紧接着 `:92-95` 的 `if (overage > 0 && !candidate.workforceReassignmentRequired)` 永远不可能成立——是对 `:88` 的重复表达，实际不可达。
- 证据（顺序敏感）：整个校验从 `:55` 到 `:377` 有 30 余个 `return false`，**首个失败即返回**，错误文本因此只反映最先命中的检查。测试用**错误文本片段**做断言，例如 `current_game_tests.cpp:442`（含"控制字符"）、`:215`（含"需要新开局"）、`save_repository_tests.cpp:294`（含"控制字符"）。重排检查顺序、或把某条检查提前，会让这些测试以"信息不匹配"的方式失败，也会改变玩家看到的报错。
- 附带观察：`:66-70` 的 `nonnegative` 数组把 `seasonLimit` 也列了进去（最后一项），而同一函数在 `:61` 已经用 `candidate.seasonLimit <= 0 || > 10000` 做过范围检查，属于冗余检查（无害，但会让读者以为 `seasonLimit` 有两套语义）。
- 建议：把 `:92-95` 删掉或在注释里显式说明其与 `:88` 的等价关系；给校验错误加稳定的错误码/枚举（而不是让测试依赖中文文本），至少让新增测试不必复制文案。

### 风险 7［中］人口归零在任务结算路径不触发覆灭

- 证据：覆灭判定集中在 `finishExtinction()`（`game_engine_season.cpp:161-170`：`population <= 0 || campDurability <= 0` → `Finished + Extinction`），其调用点只有三处：`endSeason`（`:218`）、`warAttack`（`game_engine_war.cpp:186`）、`chooseEvent`（`game_engine_season.cpp:285`）。**`executeMission` 的结算路径没有调用它**：阵亡只做 `candidate.population = std::max(0, candidate.population - deaths)`（`game_engine_mission.cpp:216`），覆灭只在"存活骨干不足以重建永久小队"时手动进入（`:270-277`，条件是 `coreSquadLost && candidate.squads.empty()`）。
- 后果：`population == 0` 但阶段仍是 `Managing`（`validateState` 只要求 `population >= 0`，`game_engine_validation.cpp:66-75`）是可以提交、可以存档的合法状态。此时 `populationCapacity` 为 0（`population_rules.cpp:50`），`workforceReassignmentRequired` 会被置真（`:56-59`），玩家被限制只能降劳力/驻军/解散军队/看事件，必须再 `endturn` 一次才会因 `finishExtinction` 进入覆灭。也就是说"部落已经没人了，但游戏还在经营阶段"这个中间窗口是真实存在的。

### 风险 9［低］地图外交提前回写 `discovered`，且不消耗部落行动点

### 风险 12［低］`chooseEvent` 不返回 `endingReached`，也不触发自动保存

- 证据：`chooseEvent`（`game_engine_season.cpp:279-287`）先 `resolveChoice` 改候选状态，再调用 `finishExtinction(candidate, outcome)`（`:285`，可能把状态改成 `Finished + Extinction`），最后 `commit(std::move(candidate), ..., false)`——第 3 个实参是 `consumesAction=false`，**`seasonAdvanced` 与 `endingReached` 都取默认 false**。
- 对比：`endSeason` 在覆灭时传 `commit(..., false, true, true)`（`:220`），`chooseEnding` 传 `endingReached=true`（`:265-266`）。
- 后果：`application.cpp:214-226` 只在 `result.endingReached` 时立刻落盘并播放结局演出、只在 `result.seasonAdvanced` 时自动保存。因此"事件导致覆灭"这一走法**不会立即播演出、也不会立即自动保存**，玩家要等到 `back`/`quit` 才落盘。状态本身是正确的（`phase=Finished, ending=Extinction` 均通过校验），属于体验与持久化时机问题。
- 建议：`chooseEvent` 里按 `candidate.phase == Finished` 决定 `endingReached`，与其它路径统一。

### 风险 14［低］渲染路径的重复构造与重复寻路

- 证据 1：`renderMission` 每帧构造 `ExpansionGame{mission}` 只为取 `lookText()`（`console_ui.cpp:481`）；该构造会 `validateState`（`expansion_game.cpp:142-145`）并复制整个 `ExpansionState`（含全部队员与装备）。因为输入一定是已提交状态（`GameEngine::validateState` 保证 `activeMission` 合法），不会抛异常，但每帧都有一次深拷贝。
- 证据 2：`missionRouteHint`（`expansion_game.cpp:410-471`）内部最多调用 3 次 `nearestWhere`（指定资源产地、最近结算点、最近未探索点，分别位于 `:437`、`:455`、`:461`），每次遍历 16 个地点并调用 `roadDistance`；而 `roadDistance` 内部又调用 `roadPath`（`world_map_catalog.cpp:273-278, 280-294`），后者每次都从零跑一遍 BFS（`roadPredecessors`，`:194-217`）。最坏情况下单次提示约 3×16×2 = 96 次 BFS。十六地点规模下开销可忽略（单次 BFS 仅 16 结点），但这是**可轻易缓存**的重复计算。
- 建议：若后续地点数或提示条数增加，把 `roadPredecessors` 的结果按起点缓存（目录是 `constexpr`，天然可缓存），或让 `ExpansionGame::lookText` 直接复用已构造的实例而不额外拷贝。

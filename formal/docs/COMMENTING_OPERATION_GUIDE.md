# 中文注释协作操作手册

本文用于在不改变《燧火纪：部落黎明》行为、命令、公开接口和存档格式的前提下，分批补充或改进正式版源代码注释。它适用于 Luna、DeepSeek 或其他代码助手；模型只能协助起草，最终取舍、审查与验证必须由负责整合的人完成。

## 1. 角色分工

| 工作类型 | 建议执行者 | 原因 |
| --- | --- | --- |
| 小而独立的接口注释、枚举说明、低风险工具函数 | Luna | 速度快，适合规则明确的机械性工作。 |
| 对已有注释的遗漏、歧义和错误进行第二视角审阅 | DeepSeek | 适合作为独立评审者，输出问题清单或候选文案。 |
| 存档、状态校验、候选状态提交、人口、任务、战争和 UTF-8 路径 | 主负责模型或人工 | 这些路径带有原子性和跨模块不变量，必须结合测试与完整上下文判断。 |
| 最终合并、格式化、构建、测试和 PR | 主负责模型或人工 | 注释不能替代真实验证，且合并者要承担回归风险。 |

不要让任一辅助模型直接批量改写整个仓库。尤其不要接受“顺手重构”“顺手改命名”“顺手修逻辑”的混合改动。

## 2. 不可突破的范围

- 只处理 `formal/include/`、`formal/src/` 中的正式版代码；测试仅为复杂夹具、二进制构造、随机命令序列和隔离策略添加必要说明。
- 不修改玩家可见的中英文/数字命令、玩法数值、公开 API、v6 存档字段顺序、校验和或恢复优先级。
- 不修改、暂存或提交 `formal/docs/TEAM_ASSIGNMENT.md`、`formal/src/.vs/`、`out/`、`saves/`。
- 不粘贴令牌、密码、Cookie、真实存档或个人目录内容给外部模型。
- 每次只处理一个职责单元或不超过三个彼此紧密相关的小文件。

## 3. 注释标准

### 3.1 函数文档

在最接近的声明或定义处只写一次 `///` 中文文档注释；已经在头文件声明处完整说明的函数，不在 `.cpp` 重复同一段文字。每个命名生产函数应尽可能说明：

1. 用途；
2. 输入和输出；
3. 状态影响，或明确“无状态修改”；
4. 失败条件；
5. 必须保持的不变量。

示例：

```cpp
/// 将已验证的候选状态原子提交为当前状态。
/// 输入：candidate 为即将替换的完整游戏状态。
/// 输出：成功时返回 true；状态非法时返回 false。
/// 状态影响：仅在完整校验通过后改写 state_。
/// 失败条件：人物、装备、任务或文本等任一不变量不成立。
/// 不变量：失败时 state_ 保持完全不变。
bool GameEngine::commit(GameState candidate);
```

### 3.2 步骤级注释

只在读者难以从代码本身看出的边界处使用简短中文 `//` 注释。重点覆盖：

- 存档临时档写入、复解析、备份轮换、替换和回滚点；
- v5→v6 原始字节归档与迁移失败不污染主档的边界；
- 候选状态验证与提交的先后顺序；
- 人口占用、任务结算、装备锁定与归还；
- UTF-8 字形解析、列宽计算和换行；
- 地图道路合法性与遭遇状态切换。

不要用注释重复显而易见的赋值、循环或条件判断。必要的 clang-tidy `NOLINT` 指令可以保留英文标识，但应在附近补充中文原因（若代码本身还没有说明）。

## 4. 推荐切片顺序

| 切片 | 文件示例 | 建议执行方式 |
| --- | --- | --- |
| A：纯目录与解析 | `command_parser.*`、`game_command_catalog.*`、`world_map_catalog.*` | Luna 起草，主负责者检查别名和数据源语义。 |
| B：文本与终端 | `console_ui.*`、`game_engine_text.cpp`、`ending_presentation.cpp` | Luna 起草，保留 ANSI、80 列与窄窗口行为。 |
| C：状态与规则 | `game_state.hpp`、`population_rules.*`、`war_rules.*`、`seasonal_event_rules.*` | 主负责者编写；DeepSeek 只做遗漏审阅。 |
| D：任务、外交、战争与季结算 | `game_engine_*.cpp`、`game_engine_internal.hpp` | 主负责者编写；按职责单元逐一测试。 |
| E：存档 | `save_codec.*`、`save_file_transaction.*`、`save_repository.cpp` | 只由主负责者或人工处理；DeepSeek 仅提供审阅意见。 |

## 5. 给 Luna 的执行提示词

每次将下列提示词中的文件范围替换为本轮实际文件，并附上相关头文件和调用方所需的最小上下文：

```text
你只为《燧火纪：部落黎明》的以下文件补充或改进中文注释：<文件列表>。

硬性约束：
1. 不改变任何可执行语句、命令语法、字符串、API、字段、序列化格式、测试断言或格式化规则。
2. 只新增或改写注释；函数只在最近的声明或定义处写一份 /// 文档注释，避免复制。
3. 每个命名生产函数说明用途、输入/输出、状态影响、失败条件和不变量；纯函数明确“无状态修改”。
4. 复杂事务仅添加短的中文步骤注释，标明原子性和回滚边界；不要给显而易见的代码逐行解释。
5. 不处理 TEAM_ASSIGNMENT.md、.vs、out、saves，也不创建或删除文件。

请先列出准备补注释的函数清单，再给出仅含注释改动的统一 diff；若无法确认语义，标记“需主负责者确认”，不要猜测。
```

Luna 的输出必须由主负责者逐段审查后再应用。一次输出涉及超过三个文件时，拆分重做。

## 6. 给 DeepSeek 的审阅提示词

建议让 DeepSeek 审阅已经产生的 diff，而不是让它直接写入工作树：

```text
请审阅下面这份 C++ 注释改动，不要重写代码，也不要提出玩法改动。

检查：
1. 是否有注释与真实控制流、失败条件或状态影响矛盾；
2. 是否遗漏原子性、回滚点、装备唯一所有权、人口占用或 UTF-8 安全边界；
3. 是否把实现细节误写成稳定 API 承诺；
4. 是否存在无意义的逐行解释或重复声明/定义注释；
5. 是否混入英文遗留说明（NOLINT 和技术标识除外）。

按“文件:行号 / 严重程度 / 原因 / 建议文案”输出问题清单。没有问题时明确写“未发现阻断项”。
```

审阅结论只是建议，不能替代阅读调用链和运行测试。

## 7. 每个切片的执行步骤

1. 在独立分支开始，记录 `git status --short`；先保护已有用户改动。
2. 阅读目标文件、其最近的声明、调用方和关联测试；先写函数清单，再请求辅助模型。
3. 仅应用注释 diff。若 diff 出现可执行代码、字符串、CMake、存档字段或测试断言变化，立即拒绝该 diff。
4. 人工核对至少一个成功路径、一个失败路径和一个状态不变路径的注释是否准确。
5. 运行格式检查和相关测试；涉及引擎或存档时运行完整 Debug/Release 验证。
6. 用中文提交，PR 标题与说明也使用中文；PR 中说明本轮只改注释还是包含了经过验证的代码修复。

## 8. 验收命令

在 `开发代码` 根目录执行。若普通输出目录被正在运行的测试程序占用，不要强行结束未知进程；改用独立构建目录验证。

```powershell
.\build-formal.ps1 -Configuration Debug
.\build-formal.ps1 -Configuration Release
cmake --build .\out\Formal-Debug --target format-check
git diff --check
```

随后直接运行对应的 `tribe-formal-tests.exe`，并记录用例计数。涉及正式版生产文件时，继续运行 `tools/run-clang-tidy.ps1`。任何测试失败、格式失败或注释与控制流矛盾，均不得提交。

## 9. 提交前清单

- [ ] 改动仅包含注释、必要的文档和对应验证记录。
- [ ] 每个新增注释与真实输入、输出、失败条件和状态影响一致。
- [ ] 未重复复制头文件和实现文件的同一段说明。
- [ ] 未改动命令、玩法、公开 API、v6 存档或玩家文本。
- [ ] `TEAM_ASSIGNMENT.md`、`.vs/`、`out/`、`saves/` 未进入暂存区。
- [ ] Debug、Release、CTest、测试程序、格式检查和静态检查已按影响范围完成。
- [ ] PR 标题、说明和提交信息均为中文，且采用普通分支、审查和 squash 合并，不 force push。

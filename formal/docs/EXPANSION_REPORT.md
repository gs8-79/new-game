# 《燧火纪：部落黎明》大型扩展版课程设计报告

## 1. 项目概述

本项目是一款使用 C++17、STL、CMake 和 Visual Studio 2026 开发的单机文字策略 MUD。大型扩展让玩家代表整个部落；V1纵切提供具名人物、装备与直接操控，V2战役提供小队常驻、外交、贸易、战争与内部稳定。

扩展采用两次迭代。V1完成从营地出发、苍林采集、外族遭遇、和平贸易或战斗、拾取并回营的纵切；V2通过 `CampaignGame` 和 `CampaignState` 把纵切嵌入六部落、16地点和8/16/32季战役，并加入版本2存档和独立结局演出。

四张设计图统一区分 V1 与 V2，见 [EXPANSION_DIAGRAMS.md](EXPANSION_DIAGRAMS.md)。

## 2. 需求分析与OOA

### 2.1 当前参与者

- 玩家：在V1培养人物、编组装备和直接战斗；在V2管理部落、小队任务、外交、贸易、战争并选择结局。
- 其他部落AI：在季节结算中根据种子、季节、关系、战争状态和贸易路线执行自主变化。
- 季节系统：结算食物、朝贡、常驻任务、事件、派系、外交变化和结局条件。

### 2.2 V1与V2用例边界

V1实际参与者只有玩家。玩家从主菜单进入扩展试玩，选择2至8人小队或固定种子，执行探索、采集、交谈、贸易、劫掠、战斗、拾取、装备和回营结算。V2新增部落经营、16地点侦察、常驻任务、六部落外交、供需贸易、派系安抚、军队战争、季节结算、结局选择和长期沙盒。

### 2.3 主要对象

- `Character`：具名角色及其属性、经验、疲劳和装备。
- `Squad`：2至8人的作业小队，包含队长、成员、任务和凝聚力。
- `Army`：战争时由统帅、正式战士和民兵组成的临时军队。
- `Item`、`Inventory`：个人装备、战利品、重量和格数限制。
- `ExpansionGame`：苍林任务的阶段、命令和原子状态修改。
- `CampaignState`：保存V2长期战役中的资源、16地点、六部落关系、派系、永久小队、活动任务、战争、结局与编年史。
- `CampaignGame`：执行8/16/32季战役、管理动作、季节结算、自主部落、任务、战争和结局条件。
- `GameEngine`：保留旧正式模式的季节经营规则。
- `SaveRepository`：严格解析、保存、备份和恢复旧正式模式的 `GameState`。
- `CampaignSaveRepository`：独立保存V2 `CampaignState`，提供6个手动档、自动档、校验和及 `.bak/.tmp` 恢复。
- `EndingPresentation`：只读显示五种结局的ASCII演出、后日谈、统计和编年史，不修改游戏状态。

## 3. OOD与模块职责

扩展没有把新规则继续塞入原有千行引擎，而是建立分层领域模块：

- `expansion_types` 只处理人物、小队、军队、装备和背包规则。
- `expansion_game` 只处理苍林任务、遭遇和可操控战斗。
- `campaign` 组合长期局面、季节经营、六部落外交、派系、贸易、战争、结局条件和编年史。
- `GameEngine` 继续处理旧正式模式，并先修复已确认的规则漏洞。
- `ConsoleUI` 分别渲染旧正式模式、V1纵切和V2战役，不直接修改状态。
- `SaveRepository` 与 `CampaignSaveRepository` 分别负责旧正式版和V2存档，不决定玩法；两者都在加载完成后再原子替换当前状态。

所有行为使用“复制候选状态→完整校验→一次提交”。条件不足、非法命令和背包超限都不会扣资源或留下半次修改。

## 4. V1玩法实现

### 4.1 角色和成长

角色拥有力量、敏捷、体魄、感知、生存、交涉、意志、统率八项属性。升级获得1个成长点，可以手动加点，也可以按职业一键推荐。疲劳会降低速度和战斗表现；休整同时受生命上限和疲劳下限保护。

### 4.2 装备和背包

个人装备栏固定为主手、副手、头部、身体、手部、腿足、工具、饰品。装备损坏时只提供一半加成，报废装备不能穿戴。背包同时检查重量和格数；拾取失败时状态不变。

### 4.3 苍林任务和战斗

任务依次经过营地准备、森林探索、外族遭遇、三段战线战斗、回营结算。玩家每回合操控队长，队员根据军令自动跟随。速度影响先手和闪避；疲劳越高，速度越低。战斗胜利后拾取不消耗回合，战斗中禁止换装。

### 4.4 可靠性修复

- 守卫加成保留到真正处理下一次岩牙来袭后再清零。
- 岩牙在来袭战中被击溃后，允许占领空要塞并完成征服道路。
- 非法战术返回错误，不再解引用空策略。
- 自动保存失败时保留当前局，并提供重试、另存、取消。
- 主档损坏或缺失时，只从通过完整校验的 `.bak`、`.tmp` 恢复。

## 5. V2长期战役实现

### 5.1 模式、世界与长期状态

`CampaignMode` 提供快速8季、课程16季和长期32季。`CampaignState` 记录资源、人口、稳定、士气、16地点发现状态、六部落档案、关系、派系、角色名单、永久小队、活动苍林任务、战争、结局和最多200条编年史。所有提交继续执行“候选状态→完整校验→原子替换”。

### 5.2 小队、外交、贸易与派系

永久小队可以执行常驻采集、巡逻、侦察、护送、训练或休整；玩家也能进入 `ExpansionGame` 苍林任务，结果会回写长期资源、小队平均疲劳、精锐经验、关系和阵亡统计。当前任务只按小队人数创建纵切队伍，尚未把长期名单中的具体人物、个人装备和个人经验完整带入并回写。外交支持交谈、送礼、贸易路线、联姻、朝贡、索贡、联盟、宣战、停战和劫掠。贸易按资源供需和关系计算，满足条件后解锁贝币。玩家部落的三个派系会经历抱怨、减产、拒绝出队、要求罢免和政变，并能产生代理或继任首领。

### 5.3 战争、季节与结局数据

战争使用统帅、正式战士、民兵、军令和三段战线；伤亡会影响人口。季节结算串联常驻任务、食物与朝贡、其他部落自主行动、派系、事件和货币解锁。联盟、征服、繁荣、迁徙、覆灭五类结局均接入5帧ASCII演出、静态回退、`EndingSummary`、重放、人物/编年史查看和长期结局后沙盒。

最终平衡复核补充了四项硬约束：单次苍林采集收益有界；防守可以削弱敌军但不能直接推进或征服；贸易、劫掠和出征需要先发现对应接触地点或战争目标；战士人数不能超过总人口。

### 5.4 当前交互入口

主菜单数字 `7/8/9` 分别进入快速、课程、长期V2战役，也支持 `campaign quick|course|long`、`战役 快速|课程|长期` 和固定种子。战役内数字、中英文命令、帮助、返回与退出已经接入。`save/load` 支持1至6号手动档和自动档；每季结算及正常返回/退出时自动保存，主菜单可用 `v2load` 继续。

## 6. STL与设计思想

- `std::array` 保存固定八项属性和八个装备栏。
- `std::vector` 保存小队成员、背包物品和命令参数。
- `std::optional` 表示空装备栏和非装备物品。
- `std::unordered_set` 检查角色名和物品编号是否重复。
- `std::clamp`、`std::min`、`std::max` 控制生命、疲劳、忠诚和资源范围。
- `std::array` 还保存16地点、六部落关系、三派系和固定建筑/技术状态，`std::vector` 保存角色、永久小队与编年史。
- 战术模块继续使用策略模式；存档使用仓库职责；扩展内容采用状态机、组合和候选状态原子提交。

## 7. 测试报告

当前 CMake 已接入战役、版本2存档、结局演出及其测试。本机 Visual Studio 2026 Debug、Release 的 CTest 均为2/2；独立程序内部为旧 Demo **33/33**，正式版/V1/V2 **73/73**。新增23项覆盖Campaign规则10项、V2存档7项、结局演出6项；其余50项继续覆盖旧正式模式、可靠存档、V1领域规则和苍林纵切。

证据等级：源码和CMake接线属于代码存在；Debug/Release `33/33 + 73/73` 属于本地自动测试通过；两条 [V2程序烟测](V2_SMOKE_TEST.md) 属于本机程序级验证。V1、V2提交与标签已经推送并用远端哈希核对，记录见 [GITHUB_RELEASE_RECORD.md](GITHUB_RELEASE_RECORD.md)。当前没有Mac实机构建、交换小组试玩或课堂验收，不能写成跨平台、交换组通过或课堂已通过。

### 7.1 测试方法与问题处理

- 单元测试直接调用领域规则，检查合法动作和失败原子性。
- 路线测试从营地出发走完和平与战斗闭环。
- `tribe-formal-tests` 同时覆盖旧正式模式、V1与V2；三个早期 Demo 属于独立的 `mud-tests`，本轮已在Debug/Release分别复测33/33。
- 存档测试覆盖7槽、任务/战争中间态、完整字段往返、错误版本、校验和、损坏档、`.bak/.tmp`恢复和替换失败。
- 结局测试覆盖五类结局各5帧、不同颜色、清屏选项、静态回退、零等待及完整结算格式。
- 审查发现“阵亡角色仍可吸收攻击并继续作战”，已改为只选择存活目标，队长阵亡立即结束任务并补回归测试。
- 审查发现“装备后物品仍留在背包且可重复装备”，已改为背包取出、旧装备回收和重复操作原子拒绝。

### 7.2 评审边界

当前可以确认“代码存在”“本机Debug/Release自动测试通过”和“V2程序烟测通过”，但不能用本组测试代替交换小组评分。交换小组的实际评分、姓名、复现步骤和反馈必须在对方试玩后填写。
